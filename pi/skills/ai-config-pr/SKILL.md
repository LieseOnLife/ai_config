# AI Config Change → ai_config PR

Every AI config change is backed up in `LieseOnLife/ai_config` (`~/repos/ai_config`). When you change any file below, **open a PR there in the same task without asking.** The PR is part of "done", not a follow-up to offer.

## Path map

| Live location | Repo path |
|---|---|
| `~/.pi/agent/skills/<name>/` (omp and pi load these; `~/.agents/skills/<name>` is often a symlink here) | `pi/skills/<name>/` |
| `~/.pi/agent/{agents,extensions,prompts,scripts}/`, `AGENTS.md`, `<repo>.md`, `settings.json`, `mcp.json` | `pi/…` |
| `~/.omp/agent/{agents,extensions,lib,managed-skills,prompts,rules}/`, `AGENTS.md`, `config.yml`, `mcp.json` | `omp/agent/…` |
| `~/.claude/{agents,commands,hooks,scripts,skills,prompts}/`, `CLAUDE.md`, `settings.json` | `claude/…` |
| `~/.codex/{agents,hooks,rules,scripts}/`, `AGENTS.md`, `config.toml`; real dirs in `~/.agents/skills/` | `codex/…`, `codex/skills/` |
| `~/.config/zed/settings.json` | `zed/settings.json` |
| `~/.config/grinch/grinch.js` | `grinch/grinch.js` |

Not backed up, so no PR: credentials (`auth.json`, `models-store.json`), `models.json`, caches, sessions, `*.db`, `skills/openspec-*` (regenerated by `setup.sh`), and `extensions/trajectory` (owned by the Trajectory installer). Skills from `~/repos/obsidian-vault-template/skills` belong to that repo, not this one.

If a path isn't in the map, check the matching `scripts/sync-*.sh` before assuming it isn't backed up.

## Procedure

1. **Name one purpose per PR.** A PR changes one skill or one behavior. If you changed two unrelated things, open two PRs.

2. **Create a worktree from fresh `main`** (never commit on `main`):
   ```bash
   git -C ~/repos/ai_config fetch -q origin
   git -C ~/repos/ai_config worktree add ../ai_config-worktrees/<topic> -b saje/<topic> origin/main
   ```
   If the branch or worktree already exists, don't delete it; use `<topic>-v2`, `-v3`, and so on.

3. **Check for collisions.** `gh pr list -R LieseOnLife/ai_config --state open`, then `gh pr diff <n> --name-only` for any PR that looks related. If an open PR touches the same file, say so in your PR, or ask Saje whether to stack on it.

4. **Bring in the change, file by file.** Copy only the files you touched between the live location and the worktree, in whichever direction holds the newest version. **Don't run `sync-*.sh` or `install-*.sh`.** They rsync whole directories with `--delete`, so they would sweep unrelated drift into the PR (or wipe live edits). Before copying, `diff` the live file against `origin/main`. If it already had uncommitted edits from an earlier session, keep them and list them in the PR as "backing up live-only edits".

5. **Update every copy of a duplicated skill.** Many skills exist under both `pi/skills/` and `claude/skills/`, and some under `codex/skills/` as well. Update each copy that exists on `main`, and install the change to the matching live location. Exceptions:
   - Codex skills listed in `codex/skills-from-pi.txt` are symlinks to the pi skill, so leave `codex/skills/<name>` alone. If that file doesn't exist on `main` yet, check whether an open PR adds it before editing the Codex copy.
   - Codex copies say `$skill-name`, not `/skill-name`. Keep that difference.
   - New skills go in `pi/skills/` only, unless Saje asks for Claude or Codex copies.

6. **Make it live.** Copy the final files to their live locations too, so the change works now and not only after merge. Restart or `/reload` isn't needed for skills; mention a restart for extensions or `config.yml`.

7. **Commit, push, open the PR:**
   - `gh` account: `LieseOnLife` owns this repo. If `gh auth status` shows another active account, run `gh auth switch --user LieseOnLife` and switch back afterwards.
   - Commit message: `<emoji> <Area>: <what changed>`, matching `git log --oneline` on `main`.
   - PR body: follow the `create-pr` skill (blockquote TL;DR, change table, Code Walkthrough, Test Plan, 🤖 footer). Describe the whole diff against `main`.
   - **Never merge.** Saje merges.

8. **Post-push.** ai_config has no CI. Still run `gh pr checks <url>` once to confirm that. If the PR is a new skill or ~50+ lines of real changes, run a `reviewer` subagent on the diff, fix the obvious issues, and surface design questions to Saje.

9. **Report** the PR URL, which live files you installed, and any collision or live-only drift you found.
